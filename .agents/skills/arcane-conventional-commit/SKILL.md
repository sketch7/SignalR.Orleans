# Arcane Conventional Commit

## Format

```
<type>(<scope>): <description>
```

- `type` and `description` are required; `scope` is used on ~75% of commits platform-wide — omit
  it only when the change genuinely isn't scoped to one area (e.g. a repo-wide `chore:` bump).
- `description` is imperative mood, lowercase, no trailing period: `add`, not `added`/`adds`.
- Body and `BREAKING CHANGE:` footer are the standard Conventional Commits mechanism
  (conventionalcommits.org) but rare in practice here — no `!` or `BREAKING CHANGE:` footer showed
  up in a 300-commit sample across 8 repos. Don't manufacture one; use a body paragraph for
  non-trivial rationale instead.
- No commitlint/husky hook enforces any of this anywhere in the platform — it's convention judged
  by review, not tooling.

## Type list

Ranked by actual frequency across hexgate, blueprint(.client), ngx, dotnet, cosmowrench(.api),
foundry, schematics:

| Type       | Use for                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------- |
| `feat`     | New capability, by far the most common type                                                 |
| `chore`    | Deps, tooling, config, skills install — no behavior change                                  |
| `fix`      | Bug fix                                                                                     |
| `refactor` | Internal restructuring, no behavior change                                                  |
| `docs`     | Docs-only change (`doc` also appears — prefer `docs`, it's ~10x more common)                |
| `ci`       | CI/CD workflow changes                                                                      |
| `revert`   | Reverting a prior commit                                                                    |
| `deploy`   | **hexgate only** — auto-generated by the CD pipeline, see below. Don't write these by hand. |

`test`/`tests`, `style`, `build`, `release`, `design` show up but rarely (a handful of commits each
across the whole sample) — fine to use where they genuinely fit, not worth defaulting to over the
list above.

## Scope conventions

- Lowercase, matches a feature area or package, not a file name: `feat(store): ...`,
  `fix(gateway): ...`.
- Multi-word scopes use a space, not a hyphen: `chore(db backup): ...`, `feat(schema field): ...`.
- `(*)` is a valid wildcard scope for a change that spans the whole repo rather than one area:
  `refactor(*): align with other projects`, `feat(*): send email on registration`.

## PR-number suffix

Squash-merged PRs get GitHub's `(#123)` appended to the subject automatically — roughly half of
all commits platform-wide carry one. Don't add it by hand; it's a side effect of the merge, not
something you type into the commit message yourself.

## hexgate's `deploy(...)` format

Only in `arcane.hexgate`, only written by `.github/workflows/deploy.yml`, never by hand:

```
deploy(gateway): v1.0.0-rc.107 [undercity.prod]
deploy(blueprint): v1.0.0-rc.7 [undercity.prod]
```

`<app>` is the deployed component, the version is the pushed image tag, and `[<stack>.<env>]`
identifies the target cluster/environment. If you're editing `deploy/<stack>.prod.versions.json`
by hand rather than letting the pipeline commit for you, don't copy this format — use a normal
`chore(deploy): ...` instead.

## Examples

```
feat(schema): add space role multiselect
fix(gateway): correct X-Forwarded header transform for Flexible SSL
refactor(*): align with other projects - including downmerge and auto bump
chore(skills): install Arcane shared skills from arcane.archives
docs(schema-template): document override precedence
deploy(cosmowrench-api): v2.3.1 [undercity.prod]
```

## Common mistakes

- Past tense (`added`, `fixed`) instead of imperative (`add`, `fix`).
- Hyphenating a multi-word scope (`db-backup`) instead of a space (`db backup`) — inconsistent
  with the rest of the platform's history.
- Hand-typing a `deploy(...)` commit outside hexgate's CD pipeline, or hand-typing the
  `[undercity.prod]` suffix on a manual `chore(deploy): ...` edit.
- Inventing a `BREAKING CHANGE:` footer or `!` marker for weight — the platform doesn't use them;
  say what broke in a body paragraph instead.
